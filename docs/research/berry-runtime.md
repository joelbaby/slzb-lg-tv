# Browser-independent LG TV control from Berry

Use the app page for Pair and keep the app backend running for commands from user-written Berry scripts. The pairing spike already demonstrated Pair → Yes, saving the key on the coordinator and re-registering with it. Earlier tests on the same MR4U and LG GX verified that native Berry HTTP can submit a power-off command using an existing registration. That test ran with exclusive access to the shared HTTP client. The remaining work is the standalone app service, cooperative HTTP ownership, and acceptance with the browser closed. [Pairing spike](pairing-spike.md)

## Script interface

Use two configurable, distinct ISC channels in the range 0–100. Automation scripts claim the command channel as public writers. The app backend reads requests from that queue and owns the result channel. A broadcast result channel gives multiple callers independent queues. Each caller subscribes before sending and reads only results with its correlation ID. With a single caller, a private result channel also works. Here “private” controls who can write. Other scripts can still read from the channel. The BeApp transport uses reserved channels that ordinary scripts cannot address. [ISC channels and claims](https://github.com/smlight-tech/slzb-os-scripts/blob/f4cae87c9f89282883061ba80b114e83cf9ffc0d/docs/modules/isc.md#L3-L57) · [Broadcast behavior](https://github.com/smlight-tech/slzb-os-scripts/blob/f4cae87c9f89282883061ba80b114e83cf9ffc0d/docs/modules/isc.md#L157-L197) · [BeApp lifecycle and channels](https://github.com/smlight-tech/slzb-os-scripts/blob/f4cae87c9f89282883061ba80b114e83cf9ffc0d/docs/modules/beapp.md#L1-L24)

- Define a small JSON request with a protocol version, `on` or `off`, a caller-unique correlation ID, and a short expiry on the coordinator uptime clock. The app uses only its own configured destination, MAC and key. A reply carries the correlation ID and a secret-free status such as `submitted`, `http_busy`, `not_paired`, `expired`, or `transport_failed`.
- `ISC.send()` confirms enqueueing. Queue exhaustion is a local submission failure. A missing result could reflect an app that is stopped, a full result queue, or a lost reply after submission. Expired requests must be dropped before performing an action. ISC retains messages when a writer stops, so validate expiry on dequeue, bound accepted TTLs, and reject invalid future timestamps. Use a bounded recent-ID cache if retrying the same request is supported. On a missing result, the caller should treat the outcome as unknown. [Queue and send behavior](https://github.com/smlight-tech/slzb-os-scripts/blob/f4cae87c9f89282883061ba80b114e83cf9ffc0d/docs/modules/isc.md#L69-L113) · [ISC lifecycle and callback restrictions](https://github.com/smlight-tech/slzb-os-scripts/blob/f4cae87c9f89282883061ba80b114e83cf9ffc0d/docs/modules/isc.md#L318-L330)
- Run command dispatch and network exchanges in the app's main loop. Poll ISC and BeApp with bounded waits so the app can service either source and preserve one execution lane for conflicting actions. A caller's timer or Zigbee event handler can send a command, then poll for its result with a zero timeout in a later callback. Timers and event callbacks are serialized across scripts. Blocking network I/O, a delay, or a blocking receive in a callback can stall other scripts. Enable the app's Start on boot option for unattended use. [ISC scheduling](https://github.com/smlight-tech/slzb-os-scripts/blob/f4cae87c9f89282883061ba80b114e83cf9ffc0d/docs/modules/isc.md#L318-L330) · [Timer restrictions](https://github.com/smlight-tech/slzb-os-scripts/blob/f4cae87c9f89282883061ba80b114e83cf9ffc0d/docs/modules/timer.md#L120-L132) · [App boot and sandbox behavior](https://github.com/smlight-tech/slzb-os-scripts/blob/f4cae87c9f89282883061ba80b114e83cf9ffc0d/docs/modules/beapp.md#L204-L219)

On can use `WOL.wake(configured_mac)` from the backend. The return value describes sending a wake packet. Wake behavior on a TV still depends on its network standby configuration. This action leaves the shared HTTP client free. [WOL API](https://github.com/smlight-tech/slzb-os-scripts/blob/f4cae87c9f89282883061ba80b114e83cf9ffc0d/docs/modules/wol.md#L16-L47)

## Off transport and ownership

The documented Berry `HTTP` object is shared by all scripts. `HTTP.isOpened()` is a read-only snapshot available on the tested firmware. A true value is sufficient to return `http_busy`. A false value can become stale before `HTTP.open()`. The published and installed API inventories expose no atomic lease, owner identity, independent HTTP instance or method for setting the connect/perform timeout. `TCP_CLIENT` is independent and binary-safe, but plain TCP only. No native TLS socket or WSS client binding appeared in the installed Berry API inventory. [HTTP shared client and API](https://github.com/smlight-tech/slzb-os-scripts/blob/f4cae87c9f89282883061ba80b114e83cf9ffc0d/docs/modules/http.md#L43-L78) · [TCP client capabilities](https://github.com/smlight-tech/slzb-os-scripts/blob/f4cae87c9f89282883061ba80b114e83cf9ffc0d/docs/modules/tcpclient.md#L28-L54)

A conservative implementation can run when the app is the sole `HTTP` user or when every relevant user cooperates:

1. Reserve a third, installation-configurable ISC channel for HTTP ownership. Each cooperating script claims it as `ISC.CH_TYPE_PRIVATE` before making any HTTP changes. A failed claim returns `http_busy` immediately. The claim grants one script writer access to the channel, so participants can use it as a lock without sending any messages. Serialize operations within each script because repeated claims by the same script succeed. [ISC exclusive claim and release](https://github.com/smlight-tech/slzb-os-scripts/blob/f4cae87c9f89282883061ba80b114e83cf9ffc0d/docs/modules/isc.md#L42-L78)
2. After claiming, check `HTTP.isOpened()`. If open, release the claim and report busy. This handles a retained client and a stale client left after a script stop. Preserve its URL, headers, mode and connection. Close only a client the app successfully opened under the lock.
3. Open HTTPS to the configured TV with stream mode and an Upgrade request, require HTTP 101, then issue masked registration and Off frames from the backend. Keep the established registration delay until measured on supported targets. The previous direct run used 800 ms between writes. Its separate TV-state checks and the user's observation confirmed power-off. Check request expiry before the power write and stop the operation on setup errors. Limit the action to one attempt with finite application waits. The native handshake and write bounds still need measurement. An ISC caller's timeout alone does not cancel an in-flight firmware call. [HTTP stream mode](https://github.com/smlight-tech/slzb-os-scripts/blob/f4cae87c9f89282883061ba80b114e83cf9ffc0d/docs/modules/http.md#L150-L158)
4. Close the owned client on every normal or handled failure path before releasing the claim. If a backend is forcibly stopped, ISC claims are released automatically and client cleanup remains dependent on the firmware. The next operation should return busy if the client remains open. A competing unmodified script can ignore the ISC claim and reconfigure the client at any point. The app must document the deployment assumption of exclusive or cooperative ownership and cannot infer it from the busy guard. [ISC claim lifecycle](https://github.com/smlight-tech/slzb-os-scripts/blob/f4cae87c9f89282883061ba80b114e83cf9ffc0d/docs/modules/isc.md#L51-L77)

The existing household lighting script reuses its `HTTP` client across successful requests and normally leaves it open. An app following the busy guard can therefore remain busy while that automation is active. The earlier live Off test paused the lighting script, separately cleared the stale HTTP object after confirming exclusive access, ran Off, and restored the original automation state. That procedure establishes the transport and cannot serve as the production concurrency mechanism. For a cooperating installation, all HTTP users need to close and release at a bounded transaction boundary. The existing unmodified lighting automation is outside that assumption.

The native write binding returns no byte count. The previous bodyless-101 fixture could not deliver the TV's registration and command replies into Berry. Report `submitted` when the upgrade succeeded and the app called both writes without an API error. A real TV can still reject an expired or revoked key, and this path cannot distinguish that from a transport failure after submission. Native HTTPS also lacks certificate verification through this API, so the certificate fingerprint learned during browser Pair cannot be enforced on this runtime path. Keep this path within the documented trusted-LAN boundary. Change the historical fixed WebSocket nonce and uptime-seeded mask before claiming RFC 6455 compliance. The nonce and fresh per-frame masks require an appropriate randomness source. [Native HTTPS caveat](https://github.com/smlight-tech/slzb-os-scripts/blob/f4cae87c9f89282883061ba80b114e83cf9ffc0d/docs/modules/http.md#L1-L8) · [WebSocket client handshake](https://www.rfc-editor.org/rfc/rfc6455.html#section-4.1) · [Client frame masking](https://www.rfc-editor.org/rfc/rfc6455.html#section-5.3)

## Acceptance still needed

Exercise the public ISC actions with the browser closed. A controlled TLS fixture should verify the order of the native registration and Off frames after a bodyless 101. Exercise a pre-opened HTTP client, a contested cooperative lock, simultaneous caller IDs, queue exhaustion, expired requests, and failure during upgrade or send. Measure the total hold time against unreachable and nonresponding peers. Verify the claimed and busy paths leave a competing script's client usable, with both scripts running. Then run Off against the paired TV and independently observe its state. These app-level and concurrent tests remain open.
